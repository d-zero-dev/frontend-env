起票する問題: $ARGUMENTS

このスキルは GitHub に投稿するが、Claude から起動してよい（`impl` と `pr` スキルが呼ぶ）。副作用は手順 6 で止める — ユーザーが下書きを承認するまで何も投稿しない。

持ち越し台帳から引き継がれた問題 — 計画ファイルの `Carry-over` 見出しの項目（`impl` 手順 12）か、マージ済み PR 本文の `## 対象外` の項目（`impl` 手順 15）— には、最小の入力、観察した出力、疑われる原因とそのファイルがすでに記録されている。その記録が手順 2 を満たすので、項目に書いてあることを再調査せず、欠けているものだけを調べる。`impl` 手順 15 経由では、手順 6 の承認が Issue 作成と PR 本文へのマーカー書き込みの 2 つの書き込みを兼ねる。そう明言して聞く

# 手順

1. **問題を把握する。** 上の説明が空なら、何が起きているかを先にユーザーに聞く。既存の報告を検索する — `gh issue list --search "<キーワード>" --state all` と `gh pr list --search "<キーワード>" --state all`。一致するものがあれば、同じ問題か別の問題かをユーザーに聞く（種別: scope）。並行セッションで重複が起きやすい
2. **原因を見つける。** ユーザーが調査を省くと明言しない限り、問題を再現し（spec テストか、後で捨てる一時スクリプト。入力と観察した出力を記録する）、原因の場所（パッケージ・ファイル・振る舞い）を特定する。本文に「未調査」「原因不明」「要調査」とは書かない — 書きそうになったら調査に戻る。機能要望や改善の場合は、現状のコードが何をしていて、変更がどこに属するかを確認することが相当する。v5（`dev`）と v6（`v6`）のどちらのラインの問題か、両方かも書く
3. **一次情報を集める。** セッションで使える検索・取得ツールで、主張の裏付けとなる一次情報を探す: D-Zero のフロントエンドガイドライン（`d-zero-dev/frontend-guidelines`。scaffold と共通カスタム要素の根拠）、仕様書そのもの（WHATWG HTML、CSS、WAI-ARIA）、依存ライブラリの公式ドキュメント（Pug、PostCSS、Vite、Storybook）。ブログ記事や要約は一次情報ではない。機能要望・改善では必須。バグでは、期待する振る舞いを仕様が決めている場合に必須
4. **ラベルを選ぶ。** `gh label list --limit 100` を実行し、存在するものから選ぶ — 記憶でラベル名を打たない。このリポジトリには種別ラベル（`bug`、`enhancement`、`documentation` 等）だけがあり、領域ラベルは無い。該当する種別ラベルを 1 つ付ける
5. **本文を書く。** 構成は次のとおり:

   ```markdown
   ## As is

   <!-- 現状の振る舞い。バグなら環境（バージョン、Node.js、OS）、最小の入力、再現手順、観察した出力 -->

   ## To be

   <!-- 期待する振る舞い、または望む結果 -->

   ## Why

   <!-- 根拠。一次情報へのリンク（ガイドラインの節、仕様の節、公式ドキュメント） -->

   ## How

   <!-- 原因の場所と提案する変更: パッケージ、ファイル、関数、アプローチ。対象ライン（dev / v6） -->
   ```

   本文に書くパスとパッケージ名は、書く前に `ls` / `npm view` で実在を確認する。タイトルは修正方法ではなく、症状か求める機能を名指しする。本文に案件のサイトや実データ由来の文言を書かない（`git` スキルのサンプル値慣例と同じ）

6. **ユーザーに確認する。** 応答の本文ではなく `AskUserQuestion`（種別: confirmation）で聞く。本文に書いた質問はターンを終わらせる。タイトル、ラベル、本文全体を見せる（本文が英語ならユーザーの言語の要約も添える）。修正を求められたら直して再度聞く
7. **Issue を作成する。** 本文を scratchpad ディレクトリのファイルに書き出してから:

   ```bash
   gh issue create --title "<title>" --label "<label>" --body-file "<path>"
   ```

   `--body-file` を使うのは、インラインの `--body` が招くエスケープの事故を避けるため。`--assignee` は付けない（トークンがコラボレーターでないと失敗する。アサインはメンテナーがトリアージで行う）

8. **報告する。** 作成した Issue の番号と URL。Issue と PR は番号を共有するので、予測せず出力から読む
