# ルール

実行中ずっと有効。最初に該当する手順だけでなく、全手順に適用する。重要なものほど先に置いてある。コンテキスト圧縮後はこのファイルの先頭しか残らないため

- **やり切る**: 手順チェックリストの全項目が終わるまで作業を続ける。止まるのは、ユーザーなしでは進めないときと、取り返しのつかない手順の前だけ。「あとで〜します」と約束してターンを終えるのは手順を終えたことにならない
- **判断基準**: 何をやるか・何を聞くか・Claude が自分で決めてはいけないことは、ルート `CLAUDE.md` の「判断基準」が決める。実装コストは基準ではない。「持ち越す」「そのままにする」「この PR ではやらない」は、質問に対するユーザーの回答としてだけ存在する
- **質問**: すべての `AskUserQuestion` は種別を名乗る。**scope**（スコープ外の問題をこの PR で直すか持ち越すか。実行できない検証も同じ種別）、**spec silent**（判断基準が決めない振る舞い）、**irreversible**（リポジトリ外への書き込み、破壊的操作）、**confirmation**（投稿前に見せる下書き・まとめ方・文面）。推奨の選択肢を先頭に置き、その推奨が判断基準に照らしてどうかを 1〜2 文で添える。「どちらでもよい」「コストがかかる」は聞く理由にならない。判断基準がすでに答えている質問は聞かずに、やる
- **スコープ厳守**: 合意したスコープを自分の判断で広げない
- **スコープ外の指摘**: 合意スコープ外のバグや問題は、気づいた時点で聞いてよく（scope 質問: この PR で直す / 持ち越す）、手順 5 と手順 12 では必ず聞く。「直す」ならスコープに加える（計画も更新する）。「持ち越す」なら計画ファイルの `Carry-over` 台帳に入れ（書式は手順 5）、手順 12 でコミット前に Issue にする。Claude の判断で先送りされるものは何もない
- **fix all の範囲**: どのレビュー手順の指摘も、コードレベルの修正・テスト追加・ドキュメント修正はその場で適用する。仕様変更やスコープ拡張を伴う指摘は Claude が決めることではなく、ユーザーへの質問
- **Findings 台帳**: 手順 6〜9 のすべての指摘を計画ファイルの `Findings` 見出しの下に表で記録する（番号、出所、`file:line`、要約、状態）。応答ではなく計画ファイルに書くのは、圧縮後も手順 12 で読めるようにするため。状態は `fixed (<それを証明するツール結果: テスト実行か diff ハンク>)`、`user: fix`、`user: carry over`、`user: leave as is` の 4 つだけ。「false positive」「minor」「pre-existing」「out of scope」という状態は無い。Claude がそう思った指摘は証拠を添えてユーザーに出し、回答が状態になる。PR 自身の行の外にある指摘は scope 質問で、「持ち越す」なら `Carry-over` 台帳へ送る
- **ループバック**: いずれかの手順で大きな方向転換や巨大なコード変更が発生したら、手順 5 からやり直す
- **ステップのスキップ禁止**: ユーザーが明示的に「スキップして」と言った手順だけ飛ばす
- **レビュー結果はユーザーの言語で**: `/code-review` と `/security-review` は英語で返る。指摘をユーザーの言語に訳して報告してから直す
- **ラインを間違えない**: v5 の作業は `dev` から、v6 の作業は `v6` からトピックブランチを切り、PR の base も同じにする（ルート `CLAUDE.md` の「ブランチ構成」）。v5 の使い方を壊す変更は `v6` でだけ行う（`git` スキルの「破壊的変更と振る舞いの変更」）
- **計画との契約**: 実行は 2 つのフェーズに分かれ、計画ファイルがその間の引き継ぎになる。承認後にユーザーがモデルや権限モードを切り替えることがあり、会話は圧縮・消去されうる
  - **フェーズ A、計画（plan モード）**: 手順 1〜3 と、コードを書く前に決められる全決定。計画が触るコードにすでに見えているスコープ外の問題を列挙して 1 件ずつ聞く（scope 質問）。計画に含まれる spec silent の選択を聞く。回答をすべて計画ファイルの `Decisions` 見出しの下に書く（fix / carry over / leave as is と、その理由）。手順チェックリストの全文、このルールと判断基準への参照、空の `Carry-over` と `Findings` 見出しを計画に埋め込む
  - **フェーズ B、実行（承認後）**: まず `echo "$CLAUDE_EFFORT"` を実行し、システムプロンプトが名乗るモデルとコマンドが出した effort を 1 行、ユーザーの言語で書く。どのモデル・effort で実行が始まるかをユーザーが見られるようにするため（`$CLAUDE_MODEL` は無い。モデルは自分のシステムプロンプトから読む）。要求される水準は無く、気づいてもらうための行であって止まるための行ではない。次に計画ファイルを読み直し、手順 4〜15 を実行する。`Decisions` はそのまま適用し、計画に無い決定だけを聞く。手順 12 でもう一度計画ファイルを読み直す
  - 複数 PR にまたがる計画では、各 PR がチェックリストを繰り返すこと、PR ごとに止まること（次のルール）を計画に書く
- **複数 PR の計画**: 1 つの PR で手順 15 を終えても、次の PR を**始めない**。下の引き継ぎをしてから報告し、ユーザーの再開指示を待つ。ユーザーは PR の間にコンテキストを消す（`/exit`、`/clear`、`/compact`）ので、会話が残っていることに依存しない

## 止まる前の引き継ぎ（複数 PR の計画のみ）

1. 残りの計画を `~/.claude/plans/<topic-branch>-resume.md` に書き出す（scratchpad はセッション限りなので使わない）。内容: 全体のゴール、完了した PR（番号と内容）、残りの PR（スコープ・アプローチ・トレードオフ）、`Decisions` と Issue 番号付きの `Carry-over` 台帳、base ブランチ、次に回す手順チェックリスト
2. セッションをまたぐメモリがあれば「複数 PR の計画が進行中」と、resume ファイルのパスと残りの一行要約を記録する
3. resume ファイルの絶対パスと残りの PR をユーザーに報告して止まる
4. 最後の PR がマージされたら、resume ファイルとメモリの記録を削除するか完了にする

# 手順

このチェックリストを応答に書き写し、進めながらチェックを付ける。

```
- [ ] 1. 合意の確認（grill-me / 計画）。計画との契約（フェーズ A）を適用
- [ ] 2. ブランチ確認（正しいラインから切ったトピックブランチ）
- [ ] 3. 制約の確認（パッケージの README と JSDoc、.claude/rules）
- [ ] 4. テストファーストで実装
- [ ] 5. 持ち越しの承認 — ここまでのスコープ外の指摘を 1 件ずつ聞いた。Carry-over 台帳を書いた
- [ ] 6. /code-review medium — 指摘を台帳に入れ、訳して全部直した
- [ ] 7. /security-review — 指摘を台帳に入れ、訳して全部直した
- [ ] 8. qa-engineer（別コンテキストのサブエージェント）— 指摘を台帳に入れて直した
- [ ] 9. product-manager（別コンテキストのサブエージェント）— 指摘を台帳に入れて直した。/code-review を 1 回再実行した
- [ ] 10. yarn lint クリーン
- [ ] 11. yarn test グリーン
- [ ] 12. 先送り項目の棚卸し — 未対応のものが残っていない。Carry-over の全項目を Issue にした
- [ ] 13. コミット済み（git スキル）
- [ ] 14. PR 作成済み（pr スキル）
- [ ] 15. マージ後: merged スキルを実行した。leftovers.mjs status が (none) を出した
```

1. 実装スコープ・アプローチ・トレードオフの合意が会話文脈で成立しているか確認する。未成立なら `/grill-me` を起動し、合意してから次へ。計画を文書にするなら「計画との契約」（フェーズ A）を適用する。どのライン（`dev` / `v6`）の作業かも合意に含める
2. **ブランチ確認**: 現在のブランチを確認し、`dev` / `main` / `v6` / エピックの base branch 上にいる場合は、作業のラインに合った base から `git switch -c` でサブブランチを切ってから進む。git worktree かどうかの確認は行わない（エージェントは worktree 起動が前提のため、あえてチェックしない）
3. **制約の確認**: コードを書く前に、触るパッケージの README（使い方の正）と JSDoc（実装詳細の正）、該当する `.claude/rules/*.md` を読む。`scaffold` を触るなら、展開先のプロジェクトで何が変わるかを `create-frontend` のスナップショットで把握する
4. 合意した計画の通りに、テストファーストで実装する。期待する振る舞いを定義する失敗テストを先に書き（使い捨ての再現スクリプトではなく spec ファイルに）、それを通す。フェーズ B ではこの手順の最初に、「計画との契約」のモデル・effort の 1 行と計画ファイルの読み直しを行う
5. **持ち越しの承認**: 手順 4 を始めてから気づいた、合意スコープ外の問題をすべて列挙する。隣接コードのバグ、別の経路が取りこぼしているケース、この PR が変えないコードにあるべきテスト、ガイドラインと食い違う既存テンプレートなど。空なら「なし」と書いて進む。各項目について、計画の `Decisions` に該当があればそれを適用し、無ければ聞く（scope 質問: この PR で直す / 持ち越す）。「直す」ならスコープに加えて手順 4 に戻る。「持ち越す」なら計画ファイルの `Carry-over` 見出しの下に 1 項目 1 箇条書きで追記する。書式は `- <最小の入力、観察した出力、疑われる原因とそのファイルを、自己完結した 1〜3 文で>`。再現が文脈にある今のうちに書くことで、手順 12 が再調査なしに Issue にできる。台帳は応答ではなく計画ファイルに置く。圧縮と `/clear` を生き延びる必要があるため
6. **`/code-review medium`**: Skill ツールで `code-review` を引数 `medium` で起動する。フォークしたサブエージェントとして動くので、結果を待つ。全指摘を `Findings` 台帳に入れ、訳して全部直す
7. **`/security-review`**: Skill ツールで `security-review` を起動する。結果を待ち、全指摘を台帳に入れ、訳して全部直す
8. **`qa-engineer` を別コンテキストで**: コードを書いたモデルに採点させない。Agent ツールでサブエージェントを起動し、`.claude/skills/qa-engineer/SKILL.md` を読ませてから `git diff origin/<base>...HEAD` をレビューさせる。プロンプトには base ブランチ、合意スコープの要約（数行）、「指摘は軽微なものも含めてすべて `file:line` で報告し、編集はしない」を書く。返ってきた指摘を全部台帳に入れて直す
9. **`product-manager` を別コンテキストで**: 手順 8 と同じ方法で `.claude/skills/product-manager/SKILL.md` を使う（ドキュメント整合 — JSDoc 配置・コメント原則・README と実装の一致 — を含む）。手順 8 と 9 は独立しているので、2 つのサブエージェントを同じメッセージで起動する。手順 6〜9 の全指摘が `fixed` か `user:` の状態になったら、`/code-review medium` をもう 1 回だけ実行する（検証 → 修正 → 再検証のループを 1 周に限る。新しい指摘は直して台帳に加え、3 周目は回さない）
10. `yarn lint` を実行し、エラーを修正
11. `yarn test` を実行し、失敗を修正。`create-frontend` のスナップショットは、意図した scaffold の変更によるものだと確認してから `yarn test:update` で更新する（`.claude/rules/spec-files.md`）
12. **先送り項目の棚卸し**: 計画ファイルを読み直す。この実行で後回しにした・飛ばした・「あとで」と書いたものを応答に列挙し、1 つずつこのセッションのツール結果に対して閉じる（指せる結果が無い項目は開いたまま）。順に: (a) 計画や会話で挙がった lint / test 以外の検証（再現、`create-frontend` で実際に展開して lint・ビルドが通ることの確認、Storybook での表示確認、dry run）— 未実行のものは今実行して出力を見せる。実行できないもの（実案件が無い等）はそう言って、ユーザーに免除か PR を開けたままにするかを確認し、免除は次のセッションが見つけられる場所に記録する (b) `Findings` 台帳の全指摘が `fixed` か `user:` の状態になっている (c) 手順 6〜9 で出たスコープ外の指摘のうち `Carry-over` 台帳にまだ無いものを、手順 5 と同じように聞く。次に **`Carry-over` 台帳の全項目を、1 件ずつ `create-issue` スキルで Issue にする**。箇条書きがそのまま再現記録であり、`create-issue` が下書きごとに `AskUserQuestion` で確認する。作成したら計画ファイルの該当項目の末尾に ` — Filed as #N` を付ける。`Filed as #N` の無い項目が 1 つでも残っている間は手順 13 に進まない (d) 確認せずに置いた前提（コマンドの出力形式、ツールの有無、フィールド名）— 今確認する (e) 先送りが diff に残す痕跡: `git diff origin/<base> | grep -nE '^\+.*(TODO|FIXME|XXX|\.skip\(|\.todo\(|skipIf\()'` を実行して出力を見せる。空でなければならない。空のリストも「何を確認したか」を添えて報告する。閉じる過程でコードが変わったら手順 10〜11 をやり直す。開いた項目が残ったままコミットしない
13. `/git` の手順でコミットする（パッケージごと、依存元から順に。全部コミットしてから手順 14 へ）
14. `/pr` の手順で PR を作成する（base は手順 2 のライン）。PR 本文の `## 対象外` は `Carry-over` 台帳をマーカーごとそのまま写したもの、`## 意図的に変更しないもの` は `Decisions` の `leave as is` の項目
15. **ユーザーから「マージした」と聞いたら**: `pr` スキルの最後の手順どおり `merged` スキルを実行し、続けてマージ済み PR の持ち越し台帳を確認する。レビュー中に本文へ項目が足されていたり、マーカーが消えていたりすることがあるため。`node ${CLAUDE_SKILL_DIR}/scripts/leftovers.mjs status <n>` を実行して出力を見せる。項目が列挙される間: `create-issue` スキルで Issue にし（箇条書きが再現記録。下書きの承認は PR 本文へのマーカー書き込みも兼ねると明言する）、`node ${CLAUDE_SKILL_DIR}/scripts/leftovers.mjs mark <n> <index> "Filed as #<issue>"` を実行する。`<index>` は直近の出力の番号で、スクリプトは残りを番号を振り直して出力する。ユーザーが Issue にしないと決めた項目は `mark <n> <index> "Not filed: <ユーザーの理由>"`。Claude はそれを決めない。出力が `warning:` 行で終わるときは `gh pr view <n> --json body` で節を読み、同じ要領で解消する。スクリプトが `(none)` を出し、その出力を見せたらこの手順は終わり
