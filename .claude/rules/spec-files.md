# 既存テストは契約

既存のテストは、すでに出荷された振る舞いを表明している。変更を通すために、書き換え・番号の振り直し・統合・分割・並べ替え・削除をしない。フィクスチャの入力も変えない（例: 新しい判定が反応しないように fixture の HTML に属性を足す）。`create-frontend` の展開結果のスナップショットも同じ扱いで、`yarn test:update` で更新してよいのは、意図した scaffold の変更の結果だと差分を読んで確認できたときだけ。どれも振る舞いの変化を diff と CI から隠すので、何かが変わったことを知る唯一の信頼できる手がかりが消える。

変更で既存テストが落ちたら、止めて、どのテスト・どのケースが落ちたかをユーザーに示し、次のどれを適用するか聞く:

1. テストはそのままにして、落ちたままにする
2. 落ちた assertion だけを反転し、元の行をコメントとして隣に残す。入力、変数、番号、テストブロックはすべてそのまま。組には次のラベルを付ける: 新しい assertion の上に `// Behavior change: <何が変わったか>` の行、元の行は `// <元の行> // previous` として残す。この語は、そういう変更のコミット本文が使う語（`git` スキル）なので、検索すればテストとコミットの両方が見つかる。issue / PR 番号は書かない（`product-manager` のコメント原則）。`BREAKING CHANGE` とも書かない。それはコミットのマーカーの名前で、付けてよいかはバージョン段階とラインで決まる
3. 新しい振る舞いのテストとして追加し、古いテストはそのままにする

「小さな変更だから」は質問を省く理由にならない — どこが最小かはユーザーが決める。
